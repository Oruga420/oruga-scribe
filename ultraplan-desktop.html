Executive summary

The relay is the asset. The extension is the mechanism.

Of the 3,161 lines of application code in this repo, 1,354 are platform neutral and 1,807 are pure browser. Broken down by subsystem the split is starker: relay/ is about 95 percent reusable, extension/ is about 12 percent. The 35 percent that carries over is the part that took longest to get right: the claude -p contract with its two measured flags, the fail-closed redaction gate with its fourteen patterns and its Luhn check, and both silent-corruption guards. The 65 percent being discarded is mechanism, and mechanism is the cheap part.

So this is not a refactor of oruga-scribe. It is a new capture layer bolted onto an existing, well-hardened writer, and the plan should be read that way. The relay ports in an afternoon. The capture layer is a ground-up build against three unrelated operating system accessibility stacks, and that is where the entire risk lives.

The single hardest problem is not screenshots, it is redaction. In the browser, the DOM says a field is a password. On the desktop there is no DOM. The accessibility layer does expose a secure-field flag on all three platforms, and it is reliable when present, but it is present maybe 60 to 80 percent of the time. Worse, the failure is shaped exactly wrong: a query that returns nothing is indistinguishable from a query that found nothing to redact. A fail-closed design becomes fail-open at that boundary. Section 05 is the answer and it is the load-bearing part of this plan.

Read this before anything else

Microsoft shipped this product three weeks ago and deliberately does not do per-click accessibility capture. microsoft/skill-recorder, 3,384 stars, MIT, Electron 43, last push today. A direct search of the codebase returns zero hits for SetWindowsHookEx and zero for AXUIElement. It reconstructs steps from video frames plus optional voice narration plus window titles, synthesized afterwards by a vision model. Exactly one file touches UI Automation, and only to read a browser address bar, hosted in a spawned powershell.exe.

Two readings, and both should be held. Either Microsoft judged per-click accessibility too fragile and too slow to ship, or they optimized for a different deliverable (a reusable agent skill rather than a document a human reads). Given that mediar-ai/terminator needs a five second timeout on File Explorer, the first reading is credible.

And here is the part that is genuinely ours, not theirs. skill-recorder's window titles, URLs, clipboard previews and screen images all upload to GitHub servers for analysis; only narration transcription runs on device. Its README tells users "Keep secrets out of your recordings" and "Please don't capture secrets", and documents no automated safeguard. Microsoft ships a redaction scanner (electron/sensitive/, built on @secretlint/core 13, MIT, liftable as code) and still tells users not to rely on it. Their architecture sends pixels off the machine, so their gate cannot be authoritative. Ours does not, which is the whole reason the redaction gate can run to completion before anything leaves. Lift their code; do not cite them as evidence the approach is sufficient.

This plan answers it with a hybrid, not a bet. Accessibility becomes enrichment, never a dependency. Every click always produces a usable step from window title plus process plus coordinates plus screenshot, which never fails and never touches a network. The accessibility name is layered on top with a hard 250 ms budget, OCR fills gaps, and vision runs once at the end over the whole session rather than per click. A missing name degrades a step. It never loses one.

The four tiers, in evaluation order

Tier 1, always, never fails, never networks. Foreground window title, process name, executable path, absolute click coordinates, coordinates normalised inside the window rect, and the screenshot. A step reading "clicked at (340, 210) in the Blender viewport" with an annotated screenshot is a legitimate SOP step. This tier is also the guarantee that the recorder never silently drops a step.

Tier 2, accessibility name and role, 250 ms budget. ElementFromPoint on Windows, AXUIElementCopyElementAtPosition on macOS, GetAccessibleAtPoint on Linux/X11. Every result is graded (UsefulElementFound, GenericContainerOnly, Failed), and the grade drives tier 3 and tells the synthesis model how much to trust the label.

Tier 3, local OCR of a 300x120 crop around the click when tier 2 returns nothing or a generic container. RapidOCR through the pure-onnx-ocr crate, roughly 50 to 80 MB, tens of milliseconds on a crop that small.

Tier 4, batched vision at synthesis, never per click. Sending a crop to Haiku 4.5 per click costs about eight cents for a 200 click session, so cost is not the objection. Latency is (400 to 1500 ms per click makes live capture feel broken), and more importantly a per-click vision call sends pixels before the redaction gate has finished deciding whether they are safe to send, which directly violates this project's fail-closed rule. Batching at the end fixes latency, makes prompt caching work, produces better labels because the model sees neighbouring steps, and lets redaction run to completion before a single byte leaves the machine.

Electron wins because it is the only option where the shell costs approximately zero. The 800 line vanilla HTML panel runs unchanged. The Node relay runs unchanged in the main process. spawn('claude', args, {env}) needs no capability JSON and no regex argument validators, and the subprocess requirement is the one thing in this architecture that cannot be compromised. Every day not spent fighting the shell is a day spent on accessibility trees, which is where this project lives or dies.

The Rust you do write is napi-rs FFI, which is the friendliest Rust there is: mostly straight-line calls into uiautomation 0.25.0, xcap 0.9.8 and about thirty lines of extern "C" for macOS. You are not writing a borrow-checker-heavy async pipeline, because the pipeline stays in Node. That is the entire difference between a 5 to 8 day ramp and a 20 to 35 day one.

There is no maintained Node binding for UI Automation on any platform. Microsoft's own workaround in skill-recorder was koffi FFI plus spawning powershell.exe to host a UIA reader. In Rust you get first-class crates for all three platforms. That is the strongest single argument for the addon.

Costs accepted, plainly: roughly 150 MB installed instead of 10, roughly 200 MB of RAM while recording instead of 60, roughly 3 s cold start instead of 1.4. For a tool you open, record with for ten minutes and close, none of those is a real cost. Tauri wins only if this ever becomes an always-on background daemon, which is exactly why screenpipe and Cap chose it.

Start from StepSnap, and lift the module rather than the app

Pimzino/StepSnap (Apache-2.0, Rust, pushed 2026-05-14) already implements this architecture. Its src-tauri/src/accessibility.rs is 650 lines with #[cfg(target_os)] arms for all three platforms and no Tauri dependency inside the element-at-point function, so it lifts cleanly into a napi-rs addon even though the shell around it is Tauri.

Its ElementInfo is already the right schema, and it solves two problems not yet started here. Verbatim from its own doc comment: "is_password is true when the focused element is a password/secure field; in that case value will be the literal sentinel [password] and callers MUST NOT log or persist the actual content." And it reads the final state of a text field after typing rather than replaying keystrokes, "more reliable than the raw keystroke stream", capping values at 2000 chars keeping head and tail.

Its Linux arm is a placeholder that returns a hardcoded string. It shells out to gdbus, calls GetAccessibleAtPoint, ignores the result and returns "UI Element". The comment says so. That is precisely what happens when someone builds this without a Linux machine, which is the strongest available argument for tiering Linux honestly rather than promising it.

Wayland: three independent blockers, any one fatal

1. There is no global input observation. No API receives clicks outside your own surface, and none reports the cursor position. xdg-desktop-portal issue 880 is an open request for a mouse-position portal that does not exist. org.freedesktop.portal.InputCapture is not passive monitoring: it is barrier triggered and exclusive, built for software KVM tools like input-leap.

2. The accessibility fallback is also dead. AT-SPI2 mouse:button events came from X and are not emitted under Wayland. This is why Orca's mouse review does not work there.

3. You cannot choose which window to capture. The ScreenCast portal does not let an application enumerate or select a window. The compositor shows a picker and returns a PipeWire node. Even with 1 and 2 solved you could not say "capture the window that was just clicked".

And a fourth, for completeness: under Wayland, AtspiComponent returns the same position whether you request desktop or window coordinates. That is not a bug awaiting a patch. Wayland deliberately does not expose global surface coordinates to clients. GNOME's next-generation accessibility protocol changes the model to client-side hit testing, and its own status is "early planning stages", no timeline.

One precision so nobody misreads the cause. evdev-based click detection through /dev/input still works, so raw input capture was never the blocker. What dies is the ability to name what was clicked, which is the entire product. A screenshot-and-OCR recorder remains technically possible on Wayland, but that is a different and worse product.

Say "not viable", not "degraded". Both accessibility agents reached this independently, from opposite directions (broken coordinates from the tree side, no mouse:button events at all from the capture side), and asked that it be recorded this way. Calling it degraded invites someone to budget two weeks for native Wayland.

Windows: a designed limitation, not a defect

Against an elevated window, UIPI splits the capabilities cleanly, and the split is what makes it manageable. Pixel capture works, because UIPI restricts window messages and hooks, not GDI or DWM reads. UIA fails: Microsoft, verbatim, "Microsoft UI Automation can't drive the UI graphics of elevated applications on the desktop without the ability to bypass the restrictions that UIPI implements." So no name, no role, no bounding rect and no IsPassword flag on admin consoles, installers and some enterprise apps. Global low-level hooks are ambiguous: no authoritative Microsoft statement exists, and community evidence says degraded, which is spike S2.

Do not pursue the uiAccess="true" remedy. It needs a signature chaining to a trusted root and installation under %ProgramFiles% or %WinDir%\System32. Far too heavy for a local personal tool, and Project Zero published "Bypassing Administrator Protection by Abusing UI Access" in February 2026, so Microsoft is tightening that path rather than blessing it.

The designed behaviour, on the record as intentional. Over an elevated window: capture the pixels, skip the outline, skip the secure-field check, mark the step unannotated: elevated target. Because the tree returned nothing, the six-point gate in section 05 then blocks that step's screenshot from reaching the model anyway. So "records everything except the admin console" is correct and safe behaviour. Write it into the spec so nobody files it as a bug later.

Tier assignment

Tier 1, Windows 11. Best API, no permissions to negotiate, the most reference code, and openstep's element classifier drops straight in. You use this machine every day. Ship here first and use it for real work before touching anything else.

Tier 2, macOS on Apple Silicon. The API is good; the work is entirely TCC and code signing. Three separate permission prompts in onboarding (Input Monitoring, Accessibility, Screen Recording), and a hard ordering constraint below. Build arm64 natively and assert the architecture, because a silently x64 addon under Rosetta works in dev and is slow and confusing in production.

Tier 3, Linux on X11 only, deferred and declared. Check XDG_SESSION_TYPE at startup. Under Wayland, say plainly in the UI that automatic click recording is unavailable and offer a manual "capture this step" hotkey, which is the only thing that works. Do not book the days until there is a machine. A VM or a cheap box running Fedora or Ubuntu with GNOME on X11, not Wayland, is a weekend of work and it is the only Linux configuration where the full architecture works today.

05 / Redaction

Fail closed becomes fail open, unless the trust model is inverted

This is the load-bearing section. Everything else is engineering; this is the part that decides whether the tool is safe to run on a machine that holds four companies' credentials.

If one line survives into the implementation spec, it is this one

Secure-field logic needs three states, not two: secure, not-secure, and UNKNOWN. Unknown fails closed.

The same bug appears four times, on three platforms, through four unrelated mechanisms, and naive code reads all four as "not a password":

PlatformMechanismWhat "unknown" looks like
macOSAX subrolekAXErrorAttributeUnsupported on a field that simply has no subrole. Not a present-but-nil value
macOSSecure event inputfalse on a password surface nobody remembered to wrap
WindowsUIANo element at all, because the target window is elevated and UIPI blocked the call
LinuxAT-SPINo tree at all: Electron with a11y off, Java without Access Bridge, Flutter, canvas

Every one of these is indistinguishable from a genuine negative unless the three states are modelled explicitly. This is the kind of defect that works perfectly in testing and leaks in production, which is exactly the failure signature this project already documents about itself.

The failure, precisely

redactionRects() returns an empty array in two situations that are indistinguishable to the caller: there was nothing to redact, and the tree could not be read. In the browser the DOM is always there, so empty reliably means the first. On the desktop, UIA IsPassword returns nothing for Electron with accessibility off, for Qt built without the a11y plugin, for Java Swing, for canvas apps, for games and for elevated windows under UIPI. So the query legitimately returns empty over a visible password field, and the blackout silently does nothing.

The web rule ("drop the step if the scrubber throws") is right and too narrow. The dangerous case is not the scrubber throwing. It is the scrubber running perfectly with nothing to look at.

Inverted trust: a step is unsafe by default and earns its way out

A frame reaches the model only if all six of these hold. Any one failing drops the step, loudly, with a named reason the user can see and act on.

  • 1. Provenance known. The target process and window were identified. Unknown process, unknown window, or a whole-screen capture instead of a specific window: drop.
  • 2. The tree was actually readable. Not "no secure fields found" but "queried and returned N greater than zero elements". A tree returning zero means zero secure-field coverage, which is exactly the leak case. Drop, or degrade to text only with no screenshot.
  • 3. Not blocklisted, and not the near-uniform-black signature of an app that protects itself with WDA_MONITOR. Treat an all-black capture as a redaction signal, not a bug.
  • 4. OCR ran and returned text. Nothing returned on a frame that visibly has text means the text scrubbers never ran. Treat as unscanned. Drop.
  • 5. No high severity detector fired (private key blocks, credential prefixes, anything the accessibility layer marked secure).
  • 6. Redaction was applied and re-verified. Blank the region in the raw buffer, then re-OCR just that rect and confirm the string is gone. Cheap, and it catches the single worst bug class: a coordinate-space mismatch that draws the black box in the wrong place.

Plus one structural guarantee: the un-redacted frame must never exist as a file. Capture into memory, redact in memory, encode once after redaction, only then touch disk. A crash between capture and redaction then leaks nothing, and there is no temporary file to forget about.

The one signal that works when the tree does not, and it is macOS only

NSSecureTextField calls EnableSecureEventInput() automatically when it becomes first responder, and while secure input is held, no other process can receive events on a CGEventTap at all (Apple TN2150). A macOS recorder therefore physically cannot observe keystrokes typed into a secure field, regardless of permission or intent.

Why this is better than every other signal discussed here: IsSecureEventInputEnabled() is a public API with zero dependence on the accessibility tree. It answers correctly for Electron apps whose tree was never built, for Java apps that expose nothing, and for elevated processes. Every other flag in this section goes blind exactly when the tree is unreadable, which is the leak case. This one does not.

And it covers the browser. Chromium ships ui/base/cocoa/secure_password_input.mm with an RAII wrapper, ui::ScopedPasswordInputEnabler, over the same pair of calls, and Electron inherits it. The convention predates Chromium: Mozilla adopted enable-on-focus and disable-on-blur back in the Firefox 1.9 era, after a report that CGEvent taps could steal HTML form passwords. Settled cross-browser convention, not a quirk that might get reverted.

The gate polarity, which is the part that matters. Secure input is opt-in per surface, and surfaces get missed: Chromium issue 452071826 (HTTP Basic Auth dialog passwords were not protected, went through the VRP, now fixed at an unknown milestone) and bug 695415 (a field changing type from text to password drops the protection). Two distinct gaps in two distinct mechanisms is not bad luck, it is the shape of an opt-in protection. So: true is strong evidence and triggers suppression. false is not evidence of safety and must never authorise shipping a screenshot. It goes on the positive side of the fail-closed gate only.

A failure mode that must be surfaced, not swallowed. Apps that call EnableSecureEventInput and never call DisableSecureEventInput leave the entire system stuck: every global hotkey in every app stops working until the offending app restarts. Known offenders include KeePassXC, 1Password, TextExpander, Raycast, and Chrome itself, which sometimes fails to release it if the cursor is still in a password field when the form is submitted. Since this tool records web apps in Chrome constantly, Chrome is our single most likely source of a stuck state. The recorder must say "keystroke capture is blocked because another application is holding secure input" rather than quietly shipping an SOP with no typing in it. kCGSSessionSecureInputPID can name the holder, but openradar 48953777 reports it returns the wrong PID when secure input was enabled from a background app, so treat it as a hint for the message and never a value to branch on.

State the asymmetry plainly in the product docs. macOS is the one platform where the operating system guarantees the password never reaches us. Windows has no equivalent (the secure desktop covers only UAC and Ctrl+Alt+Del) and Linux has none at all. On those two, our own discipline is the only thing standing between a password and the disk.

Scoping: three tiers, and visible gaps instead of silence

In the browser, the goal field scopes an origin allowlist and keeps Promise, Sesh, VCC and Price Point out of each other's recordings. On the desktop, recording is machine-wide by default, so scoping stops being a feature and becomes the load-bearing safety property.

TierWhenWhat is emitted
RECORDAllowlisted, frontmost, identity still matchesPixels, window title, control name
ACKNOWLEDGENeither allowlisted nor never-listedforeign_app { app, durationMs }. No pixels, no title, no control name
INVISIBLEOn the machine-wide never-listredacted_gap { durationMs }. Not even the app name

Why a gap step and not silence. If the user alt-tabs to 1Password, copies a token, comes back and pastes, an SOP that seamlessly skips those twenty seconds is wrong: a reader following it hits a hole with no marker. The gap step is the fail-loud form, and it is also what makes the tiering testable.

Browser windows are the worst case, and the answer reuses what already works. One Chrome process hosts personal Gmail and a Promise console in different tabs, so allowlisting Chrome by bundle id allowlists all of it. Hand browser windows off to the existing extension, which knows the real origin, and have the desktop recorder emit only the "switched to Chrome" boundary. That closes the largest leak with code that is already written and already tested, and it is an independent argument for keeping both apps in one repo.

Identity is re-asserted per step, not once at Start, because a window's identity can change with no navigation event at all: a Slack workspace switch, a terminal running ssh prod. A title that flips to another company's pattern pauses and asks.

Keystrokes: the hook is a classifier, not a recorder

The insight that makes this tractable: an SOP does not need the text, it needs the semantics of the text. "Typed the project name" is a better step than "typed acme-migration-q3", because the next reader has a different project name anyway.

Never buffer plaintext, not even to scrub it afterwards. A crash, core dump, swap-out or log flush between buffer and scrub is a plaintext leak. On each key event the hook makes exactly one decision and emits a KeyClass enum, never a character. Printable characters are counted, not stored: the buffer is an integer and some flags.

Shortcuts are the exception and are safe verbatim. Ctrl+S, Cmd+Shift+P, Alt+Tab carry no secrets and are by far the most SOP-relevant keyboard events. Nearly all the keyboard value lives here.

On burst end (focus change, Enter, Tab, or about 800 ms idle) query the accessibility layer once for the focused element. Flagged secure: emit "entered a password" and do not record the length, because password length is itself a secret. Readable and not flagged and passing the six-point gate: read the element's current value, which never sees a backspaced typo or a password typed into the wrong field. Not readable at all: emit "typed N characters" and never reconstruct from keystrokes.

Fail closed on focus ambiguity. If focus changed mid-burst and the keystrokes cannot be attributed to one element, discard the whole burst. Ambiguous attribution is exactly how a password typed into a field the user had not yet clicked into ends up in a transcript.

What the commercial tools do, which is avoid the problem

UiPath Task Capture, verbatim: "The metadata for each action includes only the first letter of the keyboard input... However, all the keyboard inputs are processed in the same way so sensitive data can't be automatically recognized nor blurred/removed." They abandoned classification and truncated everything.

Teramind, a commercial DLP vendor, documents its own failure openly: password field detection works only if the field is visibly masked or its name contains "pass", otherwise the agent "will treat the field as a normal text field and capture all keystrokes entered into it, even if the 'Monitor keystrokes in password fields' option is disabled." That is a vendor admitting their privacy toggle fails open. Do not repeat that design.

Power Automate offers no automatic protection at all; the documented remedy is the user selecting a step and choosing Delete screenshot. Scribe and Tango both do OCR-based blur at capture, with automatic PII detection gated behind Enterprise tier on Tango.

06 / Execution

The plan as a dependency graph

Phases at the same indent level run in parallel. The two gates are hard stops that need your judgement, not just green tests.

Phase 0. Five spikes, before any construction All parallel

Depends on nothing / about 2 days total / each one can invalidate a plan assumption
  • S1. macOS signing and TCC, on the M5. Build a trivial .app bundle, sign with a free Apple ID Personal Team Apple Development certificate, and check whether CGPreflightScreenCaptureAccess() returns true. Decides whether you owe Apple 99 USD a year. Half a day.
  • S2. The two macOS launch paths, which now conflict. TCC attributes permissions to the responsible process, so launching via open or Finder attributes them to the app, and launching from a terminal attributes them to the terminal. That argues for open. But the "silent disable race" cuts the other way: after re-signing, a CGEventTap installed via Launch Services can be non-nil and receive zero callbacks, while running the Mach-O directly works. This is the only genuine unresolved conflict in the macOS design. Test both paths and pick per permission if necessary. Keeper line: a non-nil tap is not a healthy tap. 30 minutes.
  • S3. Windows low-level hooks over focused elevated windows. Microsoft's docs are silent on whether WH_KEYBOARD_LL receives keystrokes destined for elevated windows; community evidence points to degradation. Pixel capture and UIA behaviour are already settled (see section 04); this is the one piece still open. 30 minutes.
  • S4. Does Chromium expose input[type=password] as AXSecureTextField on macOS? Demoted from a correctness gate to a labelling nicety. Chromium calls EnableSecureEventInput for password fields regardless, so the tap goes deaf either way, and deafness is the property that actually protects the keystrokes. This spike now only decides whether the step reads "entered a password" or "typed into a field". 30 minutes.
  • S5. Is the WGC yellow border actually absent from captured frames? Multiple secondary sources assert it; no Microsoft document states it. If it is present, hiding it needs package identity via a sparse MSIX, which is a real build. Cosmetic only. 5 minutes.

Phase 3. The Windows capture layer

Depends on 2.2 / about 5 to 7 days / this is the cost centre
  • Capture the element on mouse DOWN, emit the step on mouse UP. The UI is stable before the click, not after, and on a click that opens a modal, capturing on up can block. This is the highest-value line in the entire research.
  • Never call UIA from the hook callback. Queue and return. A slow WH_MOUSE_LL procedure stalls input for every process on the machine.
  • element_from_point_build_cache with a CacheRequest covering Name, ControlType, LocalizedControlType, AutomationId, BoundingRectangle and IsPassword. One cross-process round trip instead of six. terminator uses no CacheRequest anywhere, and its own timing logs show why that hurts.
  • 250 ms timeout, not 5000. terminator needs five seconds on File Explorer because it is an automation driver where a wrong element is a failed run. A recorder already has the screenshot: a missing name costs a nicer label, a five second freeze costs the product.
  • Port openstep's candidate scoring: walk the raw view to depth 4, filter to useful control types, order by smallest area then distance from the click. It is the difference between "clicked the Save button" and "clicked the Pane".
  • WGC via CreateForWindow, with IncludeSecondaryWindows on, because a click on a dropdown or context menu item lands in a separate popup HWND and without it the screenshot will not contain the thing that was clicked.
  • Manifest as Per Monitor v2 and assert the DPI context at capture time, not at startup, because a dependency can reset the thread's context.

Phase 4. Settle, coordinates, and the step coalescer Parallel with 3

Depends on 2.2 / about 4 to 5 days
  • Settle race, four entrants, first to fire wins. Frame difference on a 64x64 grayscale sample at about 10 fps (the 32x32 diff math already exists in shot.js:185-209), accessibility structure events as an accelerator, window title change as the desktop analogue of webNavigation.onCommitted, and the existing 2500 ms ceiling. Four amendments: accessibility silence never wins, only activity followed by quiet; frame stability requires two consecutive stable samples and a frame that is neither uniform nor byte-identical to the previous step's; title change restarts settle against the new window; and add a floor of about 120 ms, which the browser never needed because a low-level hook sees the event before the target app does.
  • Open a persistent capture stream at Start rather than a one-shot per click. Once open, 10 fps of downscaled frames is nearly free, and the browser's 550 ms quota scheduler disappears entirely.
  • The coordinate invariant: never transform a coordinate, only intersect a rect with the frame that carried it. Every rect is tagged with its space, origin id, scale and frame sequence. An untagged rect throws. The only permitted conversion comes from the frame's own metadata, so both scale and origin are per frame, which kills the mixed-DPI class outright.
  • Plausibility band before drawing. The target rect must sit fully inside the frame and occupy between 0.01 and 60 percent of it. Outside that band, ship the screenshot with no outline and tag the step outline_unverified. That converts "the outline is in the wrong place" from a silent wrong SOP into a visible caveat, for free.
  • Calibration probe at Start, on every monitor the session touches. You know your own panel window's rect exactly, so predict where it lands in a capture, capture, and locate it. More than 2 px of disagreement refuses the session and names the display.
  • The coalescing state machine, which has no browser counterpart. Raw input events are not steps: right-down plus menu-open plus item-click is one step, a menu bar traversal is one step with a path label, two downs inside 400 ms and 4 px is one step.

Phase 8. macOS

Depends on Phase 7 passing / about 8 to 12 days
  • AX tree reader, ScreenCaptureKit at a macOS 14 floor (below that there is no one-shot API), and the TCC onboarding flow.
  • Request Input Monitoring before touching the accessibility check. rdar://7381305: IOHIDRequestAccess() does not work if accessibility status was previously checked via AXIsProcessTrustedWithOptions(NULL). Get this order wrong and you cannot obtain both permissions in one app.
  • Use .listenOnly tap mode, not .defaultTap: smaller permission, and it cannot accidentally eat the user's clicks. Handle kCGEventTapDisabledByTimeout and re-arm.
  • The blurry screenshot trap: SCStreamConfiguration.width/height are in pixels, SCWindow.frame is in points. Set the config straight from the frame and you get a low-res image upscaled to display size, which destroys OCR and halves effective resolution on Retina. Multiply by pointPixelScale.
  • IsSecureEventInputEnabled() polling at every keystroke burst boundary, plus stuck-state detection with a user-visible error naming the holding app. This is a genuine capability gain over Windows and Linux, not a caveat. See section 05.
  • A non-nil tap is not a healthy tap. Poll tapIsEnabled() on a roughly 5 s timer and reinstall, handle kCGEventTapDisabledByTimeout and kCGEventTapDisabledByUserInput, and preflight with CGPreflightListenEventAccess().
  • Ship unsandboxed, which forecloses the Mac App Store. App Sandbox blocks the Accessibility grant outright: AXIsProcessTrusted always returns false, the prompt never appears, and the app cannot be added manually in System Settings. Confirmed across four Apple forum threads. That is a distribution decision, not just a technical one, and for a personal local tool it costs nothing.

Phase 9. Linux, X11 only, deferred

Depends on hardware existing / about 5 to 8 days once it does
  • AT-SPI via the atspi crate 0.30.0. StepSnap's Linux get_focused_field_value is fully implemented against it and sits in the same file as the stub, so the missing half has a working reference beside it.
  • XComposite plus XShmGetImage for capture, XInput2 raw events for input.
  • The high-leverage trick: set ScreenReaderEnabled=true on org.a11y.Status at startup. Chromium, GTK and Qt applications then build their accessibility trees retroactively, without relaunching. Without it every Electron app on the machine is invisible. Side effect worth knowing: on GNOME this can launch Orca.
  • Read joshii-h/stepshot first (0BSD licence, the most permissive that exists). It proves this architecture on the hardest platform, using /dev/input evdev to bypass Wayland entirely.

09 / Your call

Four decisions I did not make for you

1. One memory, or two

The monorepo recommendation gives one MemPalace wing and one wiki covering two front-ends, which is what keeps the redaction gate in one place with a test across it. A separate repository would give the desktop product its own clean memory identity from day one. That is the one legitimate argument for option C and it is yours to weigh. Everything else favours the monorepo.

2. Linux: defer, or buy a box

WSL2 Ubuntu is not a substitute. It has no real compositor, no session D-Bus with a desktop on it, no AT-SPI registry and no PipeWire portal. Building the Linux leg there would be writing code you cannot run, which is exactly how StepSnap ended up with a stub that returns "UI Element". Options: defer entirely (recommended), a 150 to 300 USD mini PC or old laptop running Ubuntu GNOME on X11, or a cloud desktop VM which handles AT-SPI and X11 but is poor for the part that needs testing.

3. Bug 22, inherited and still open

The opt-in Opus checkbox was never built, so MODELS.synthesizeUpgrade is unreachable. Two clean ways out: build the toggle, or delete the slot and the branch. Leaving a live branch no caller can reach is exactly the shape of the ten bugs that returned success while broken. The desktop app inherits this either way, so decide it now rather than duplicating it.

4. The isolated personal login, still not done

The relay currently answers on 127.0.0.1:8787 with configDir: C:\Users\chuck\.claude, which is the work seat. Every synthesis call this project makes is spending Promise quota. The desktop app multiplies this, because it will be run far more often than the extension. One OAuth login closes it and it blocks nothing else.
